# L3.1: workload and parameter bindings on the Ledgerline benchmark database

What this is: the real workload that `pg_stat_statements` recorded after a short k6 run against the 10,000,000-row benchmark database, and what Ledgerlens (`pnpm workload:report`) did with it. Nothing here is estimated; every number comes from the raw files listed at the end.

## How the workload was produced

- `ledgerlens/scripts/k6-workload.sh` (new; the existing k6 scripts are used unchanged): pg_stat_statements reset **for the benchmark database only**, then four 95-second scenarios one after another: `usage-read` huge tenant at 2/s, `usage-read` small tenant at 2/s, `balance` small tenant at 100/s, `ingest` small tenant at 20/s. Ingested rows were removed afterwards (the table is back to exactly 10,000,000 rows).
- k6 exit code 0 in all four runs. The API ran as a host process (`HOST=0.0.0.0 pnpm --filter @ledgerworks/ledgerline dev`), on the laptop described in `docs/benchmarks/baseline.md`. This is a short run to fill the statistics, not a benchmark; no latency from it is quoted.
- The statistics cover 2026-10-04 18:40:31 UTC (the reset) until the report at 19:35 UTC.

(The report also lists `other_database`: rows of other databases on the same server, 202 in the final run because the test suite creates scratch databases there. They are not part of this database's 51.) The exclusion counts differ between the report files because Ledgerlens' own report runs and the tests add rows; the final file is the record.

**There are only 8 statements, so "the top 20" is all of them.** The Ledgerline API runs few distinct statements. One of the 8 (`SELECT count(*) FROM usage_events`, rank 1, 1 call, 3.07 s) is the preflight check of `k6-workload.sh` itself, not the application; it is left in because the report must not hide what pg_stat_statements recorded.

## Bindings, with provenance (all 8 statements, which are also the top 8)

| provenance                      | statements                                                                       |
| ------------------------------- | -------------------------------------------------------------------------------- |
| user-supplied                   | 0 (no values file was given)                                                     |
| sampled-from-stats              | 4 (ranks 3, 4, 6, 7; the INSERT is "low" confidence, the three SELECTs "medium") |
| synthesized                     | 0                                                                                |
| no parameters (nothing to bind) | 1 (rank 1)                                                                       |
| **unverifiable**                | **3** (ranks 2, 5, 8)                                                            |

So **5 of 8 statements (62.5%) have bindings or need none; 4 of 8 (50%) got sampled values**. The server accepted (plain `EXPLAIN` with the values as bound parameters) every set of the 3 sampled SELECTs; the INSERT was not checked on the source (writes are only checked on a shadow, later).

In the LIMIT/OFFSET and `to_char` format / `AT TIME ZONE` positions the values are fixed defaults (LIMIT 50, OFFSET 0/100/1000, zone `UTC`, a generic format). They are labelled `synthesized` and `structural` per parameter, and they do not lower the provenance of the set, because they do not change which rows are read (D47).

## The unverifiable statements and why

| rank | calls  | statement (normalized)                                                                             | reason                                                                                                                                                                                                   |
| ---- | ------ | -------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 2    | 11,890 | `SELECT tenant_id, api_key_id FROM ledgerline_fn.authenticate_api_key($1)`                         | `param_without_column_or_type`: `$1` is an argument of an application function, not compared with a column. A key hash cannot be guessed from statistics. A user-supplied value is the way to verify it. |
| 5    | 11,890 | `SELECT k.tenant_id, k.id FROM public.api_keys k WHERE k.key_hash = p_key_hash AND ...`            | `bindings_rejected_by_server` (42703): this is the body of the function above (it ran inside a function: `p_key_hash` is a variable that only exists there), so it cannot be run alone.                  |
| 8    | 1,802  | `SELECT $2 FROM ONLY "public"."tenants" x WHERE "id" OPERATOR(pg_catalog.=) $1 FOR KEY SHARE OF x` | `param_without_column_or_type`: `$2` is in the select list. This is the foreign key check that PostgreSQL runs inside the `INSERT` into `usage_events`.                                                  |

These three are the application's authentication path (2 and 5) and a PostgreSQL-internal statement (8). They are listed in the report; none was skipped.

## Things this run showed

- The first versions of the binder left more statements unverifiable (5 of 8, then 4 of 8): the INSERT with `COALESCE($2::timestamptz, now())`, `RETURNING to_char(... AT TIME ZONE $6, $7)` and the keyset pagination `(occurred_at, id) < ($4, $5)` were not understood at first. The raw files of those earlier versions are kept under their own names (`l3.1-workload-bindings-20261004T192437Z.json`, `...T192956Z.json`, `...T193037Z.json`); the one to read is `...T193524Z.json`.
- The application's hottest statement by calls (`authenticate_api_key`, 11,890 calls, 2.7 s) was first classed "no user tables" and excluded; a statement that calls an application function is application work, so that rule now checks `pg_proc`.
- Sampled values are **not** written to the raw JSON (they can be real ids or emails); `--include-values` writes them.
