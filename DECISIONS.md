# Ledgerworks: DECISIONS.md

One entry per decision: options considered, choice, reason. Newest at the bottom.

## D1. Language and runtime: TypeScript (strict) on Node 22+

- **Options:** TypeScript, Go, Python.
- **Choice:** TypeScript with `strict` enabled, on Node 22 or newer.
- **Reason:** Specified in plan.md section 1. One language across API, UI, core and evals; strict mode catches errors at compile time.

## D2. Package manager and layout: pnpm workspaces

- **Options:** pnpm, npm workspaces, yarn.
- **Choice:** pnpm workspaces in a single monorepo.
- **Reason:** Specified in plan.md. Fast installs, strict dependency resolution, simple cross-package linking.

## D3. Database: Postgres 16 in Docker

- **Options:** Postgres 16, other Postgres versions, MySQL.
- **Choice:** Postgres 16 run through Docker Compose.
- **Reason:** Specified in plan.md. Row-level security, partitioning, `FOR UPDATE SKIP LOCKED` and `pg_stat_statements` are all needed by the project.

## D4. API framework: Fastify

- **Options:** Fastify, Express, Hono.
- **Choice:** Fastify.
- **Reason:** Specified in plan.md. Built-in schema validation and good performance.

## D5. Tests: Vitest

- **Options:** Vitest, Jest, node:test.
- **Choice:** Vitest.
- **Reason:** Specified in plan.md. TypeScript support without extra configuration, fast, workspace-aware.

## D6. Load testing: k6

- **Options:** k6, autocannon, wrk.
- **Choice:** k6.
- **Reason:** Specified in plan.md. Scripted scenarios with built-in percentile reporting and raw output export.

## D7. UI: React + Vite (where a UI is needed)

- **Options:** React + Vite, Next.js, no UI.
- **Choice:** A small React + Vite app, only where a UI is called for.
- **Reason:** Specified in plan.md. The UI is an admin and visualization layer, so a SPA is enough.

## D8. LLM access: provider-agnostic, no vendor SDK

- **Options:** a single vendor SDK, an abstraction library, our own interface.
- **Choice:** One `LLMProvider` interface with a generic OpenAI-compatible adapter and a hand-written agent loop.
- **Reason:** Specified in plan.md. Works with free-tier and local providers, and no vendor lock-in.

## D9. Lint, format and CI tooling

- **Options:** ESLint + Prettier, Biome.
- **Choice:** ESLint (flat config, typescript-eslint) and Prettier. CI on GitHub Actions running lint, typecheck and test.
- **Reason:** plan.md asks for ESLint and Prettier by name. Both are widely known.

## D10. Local database resource limits

- **Options:** no limits, limits sized to the host, small fixed limits.
- **Choice:** The `postgres` service is pinned to **2 CPUs** and **2 GiB memory** (`cpus: "2.0"`, `mem_limit: 2g`, `memswap_limit: 2g` so swap cannot hide memory pressure). Postgres settings are sized to match: `shared_buffers=512MB`, `effective_cache_size=1536MB`, `work_mem=16MB`, `maintenance_work_mem=128MB`, `max_connections=100`.
- **Reason:** plan.md section 1 rule 5 requires container limits to be recorded next to every benchmark. Fixed limits make results comparable across machines and runs. The values are a modest, reproducible profile that fits on a laptop; they are not tuned for peak throughput. The same numbers appear in `docker-compose.yml` and must be quoted in every benchmark report.
- **Extension:** `pg_stat_statements` is loaded through `shared_preload_libraries` and created at first init by `docker/initdb/01-extensions.sql`. `pg_stat_statements.track=all` so nested statements are counted.
- **Image:** `postgres:16`, Docker Hub official image. Local only; the compose file contains a development password and is not meant for any shared environment.

## D11. Migrations: plain SQL files with a small custom runner

- **Options:** a migration tool (node-pg-migrate, Flyway, dbmate, Atlas) or plain SQL files with our own runner.
- **Choice:** numbered plain SQL files in `ledgerline/migrations/` (`0001_schema.sql`, ...) applied by `ledgerline/src/db/migrate.ts`. Forward-only (no down migrations).
- **Reason:** the schema depends on Postgres features (roles, RLS, partitioning, `SECURITY DEFINER` functions) that ORMs and generators handle poorly, so raw SQL is the honest source of truth. The runner is about 100 lines: each file runs in its own transaction, applied versions are recorded in `schema_migrations` with a SHA-256 checksum, editing an already-applied file is an error, and a Postgres advisory lock stops two runners racing. Re-running is a no-op. Later phases (Ledgerlatch) analyze these same SQL files.
- **Cost:** no automatic rollback and no drift detection beyond checksums. Acceptable for this project.

## D12. Database roles

- **Options:** one role for everything; owner + app role; owner + app + a `BYPASSRLS` auth role.
- **Choice:** three non-superuser roles, created by the runner's bootstrap step (which needs a superuser connection, the compose user, via `DATABASE_ADMIN_URL`):
  - `ledgerline_owner`: `NOLOGIN`, owns every table and function; migrations run as this role through `SET ROLE`. Under `FORCE ROW LEVEL SECURITY` it is subject to policies like anyone else.
  - `ledgerline_app`: `LOGIN`, no `BYPASSRLS`, owns nothing, cannot create objects. The API connects only as this role (`DATABASE_URL`). Least-privilege grants per table are in `0001_schema.sql`: no UPDATE/DELETE on `credit_ledger`, `usage_events`, `dead_letters`; no writes at all on `tenants` and `users`.
  - `ledgerline_definer`: `NOLOGIN`, owns the `SECURITY DEFINER` functions (see D14).
- **Reason:** a table owner can bypass RLS unless `FORCE` is set, and a superuser or `BYPASSRLS` role always bypasses it, so the app must be none of those. The app password defaults to a development value (`LEDGERLINE_APP_PASSWORD`); set a real one anywhere shared.

## D13. Schema design and indexes

- **Ids:** `uuid` (`gen_random_uuid()`) for entities; `bigint identity` for append-only logs (`credit_ledger`, `job_attempts`, `dead_letters`). Identity columns on a partitioned table are avoided, so `usage_events` uses a uuid.
- **Users are global**, tenancy lives in `memberships`; `users` has no `tenant_id`.
- **`usage_events`:** range-partitioned by month on `occurred_at`, primary key `(id, occurred_at)` (the partition key must be in every unique constraint). The migration creates 48 monthly partitions, 2024-01 to 2027-12, deterministically, plus `create_usage_events_partition(date)` for P1.10's automatic creation. There is no default partition; an event outside the range is rejected (the API maps this to a 422).
- **Composite foreign keys** `(tenant_id, job_id) -> jobs (tenant_id, id)` on `job_attempts` and `dead_letters`, so a child row cannot reference another tenant's job.
- **Indexes added (and why)** - kept deliberately few so later phases have room to improve:
  - `users (lower(email))` unique: email identity.
  - `memberships (tenant_id, user_id)` unique: prevents duplicates, serves tenant lookups.
  - `api_keys (key_hash)` unique: the auth lookup path; `api_keys (tenant_id)`: tenant FK.
  - `usage_events (tenant_id, occurred_at)`: the one main read pattern (per-tenant time range); created per partition automatically.
  - `credit_ledger (tenant_id, id)`, and a partial unique `(tenant_id, idempotency_key)`: tenant reads and idempotent debits (P1.8).
  - `jobs (tenant_id, id)` unique (composite FK target), partial unique `(tenant_id, idempotency_key)`, and partial `(queue, run_at) WHERE status = 'queued'` for the worker poll (P1.9).
  - `job_attempts (job_id, attempt_no)` unique: attempt numbering and job FK.
  - `dead_letters (job_id)` unique, `(tenant_id, dead_at)`.
- **Deliberately not indexed:** `memberships.user_id` (users are never deleted), `usage_events` by event type or metadata, `job_attempts.tenant_id`. These are where the optimization work in P1.10 and Ledgerlens can show measured effects.
- **Append-only ledger:** enforced three ways: no UPDATE/DELETE/TRUNCATE privilege for the app role, a row trigger rejecting UPDATE and DELETE, and a statement trigger rejecting TRUNCATE (so even a superuser mistake is stopped).

## D14. Row-level security design and the API-key lookup problem

- **Tenant context:** the API opens a transaction and runs `SELECT set_config('app.tenant_id', '<uuid>', true)` (`true` = local to the transaction, so it cannot leak to the next user of a pooled connection). The helper `app_tenant_id()` returns the uuid, or NULL when the setting is missing, empty or malformed. Policies compare `tenant_id = (SELECT app_tenant_id())`; NULL never matches, so a missing setting means zero rows, not an error and not everything. The `(SELECT ...)` wrapper makes Postgres evaluate it once per statement.
- **Enable and force:** `ENABLE` and `FORCE ROW LEVEL SECURITY` on all ten tables, so the owner role obeys policies too. Policies are `TO ledgerline_app` only. `credit_ledger` has SELECT and INSERT policies and nothing else. `tenants` and `users` are readable only for the current tenant (users via membership) and have no write policy for the app.
- **API-key lookup (options):** (a) a `BYPASSRLS` auth role, (b) a policy on `api_keys` that allows lookup by hash, (c) a narrow `SECURITY DEFINER` function.
- **Choice:** (c). `ledgerline_fn.authenticate_api_key(hash)` returns only `(tenant_id, api_key_id)` for a non-revoked key whose full hash matches. A second function, `ledgerline_fn.create_tenant(...)`, creates a tenant, its owner membership, a zero balance and the first key hash, because the app role has no write access to `tenants` or `users`.
- **Why not (a) or (b):** `BYPASSRLS` is all-or-nothing and would be a standing risk. A hash-lookup policy on `api_keys` would also expose key rows to any tenant that guessed or knew a hash, and mixes auth logic into data policies.
- **How the definer is contained:** both functions are owned by `ledgerline_definer` (`NOLOGIN`, no `BYPASSRLS`, not a superuser). It has table privileges only on what the two functions need (`tenants`, `users`, `memberships`, `api_keys`, `credit_balances`) with permissive policies on exactly those tables, and nothing at all on the ledger, jobs or usage data. Functions pin `SET search_path = pg_catalog, pg_temp` and reference tables schema-qualified, which blocks search-path hijacking. `EXECUTE` is revoked from `PUBLIC` and granted only to `ledgerline_app`.
- **Risks that remain:** (1) whoever can run `set_config('app.tenant_id', ...)` on an app connection chooses the tenant, so the API must set it only from the authenticated key and never from request input; the database cannot defend against a compromised API process. (2) `authenticate_api_key` is an oracle: anyone with app-role access can test hashes, which is harmless because keys are 256-bit random and only their hash is compared. (3) `create_tenant` lets a caller attach any email as owner of a new tenant; it grants no access to existing tenants. The HTTP endpoint is optionally gated by a token (D16).
- **Partitions:** RLS is declared on the partitioned parent. The app role has no privileges on the individual partitions, so they can only be reached through the parent (tested).
- **Migration/seed note:** because the owner is also subject to `FORCE`, bulk seeding (P1.6) must either run as a superuser or set the tenant per statement.

## D15. Isolation test strategy

- **Choice:** a table-driven matrix in `ledgerline/test/isolation.test.ts`: every tenant-owned table x {SELECT, INSERT, UPDATE, DELETE} x {tenant A, tenant B, no tenant set, a role with no grants}, run as the real application role over a real connection (not by `SET ROLE` from a superuser). Each cell asserts the specific failure mode: a privilege error where the app was never granted the operation, an RLS violation for cross-tenant inserts and tenant-moving updates, and zero affected rows for cross-tenant reads, updates and deletes. Positive controls (own-tenant reads, own-tenant inserts) make sure the denials are not simply because everything fails. Extra guards cover malformed tenant settings, `row_security = off`, `SET ROLE`, disabling RLS or triggers, ledger immutability, direct partition access, grants matching the matrix, and the definer functions.
- **Verified to bite:** with the `jobs` policy temporarily changed to `USING (true)`, the matrix failed on the jobs cells.
- **Output:** the run prints `ISOLATION SUMMARY: N isolation tests, M isolation assertions`.
- **Where Postgres comes from:** locally the docker-compose Postgres (database `ledgerline_test`, recreated and migrated by a Vitest global setup); in CI a `postgres:16` service container.

## D16. HTTP API design (P1.5)

- **Validation:** Fastify's built-in JSON Schema validation (Ajv), with `additionalProperties: false` on every body and query, `removeAdditional` and `coerceTypes` off (so `"name": 123` is rejected rather than silently turned into a string). Options considered: Zod or TypeBox with a Fastify type provider. Built-in schemas were chosen to avoid another dependency; the cost is hand-written TypeScript types next to the schemas. `limit` is a digit string parsed by the handler because query strings are always strings and coercion is off.
- **Authentication:** `Authorization: Bearer <key>`. Key format `lk_<8 hex>_<43 base64url>` (256-bit secret). Only the SHA-256 hash is stored, plus the visible prefix. A plain fast hash is appropriate here because the key is high-entropy random, so there is nothing to brute-force; a slow password hash would only add request latency. Malformed, unknown and revoked keys all return the same 401 with `WWW-Authenticate: Bearer`, and authentication runs before body validation. Lookup goes through the `SECURITY DEFINER` function from D14.
- **Tenant per request:** authenticated handlers run `withTenant()`: one transaction, `set_config('app.tenant_id', <id from the verified key>, true)`, commit or rollback. The tenant id is never read from request input (a body containing `tenant_id` is rejected as an unknown field).
- **Tenant creation:** `POST /v1/tenants` returns the raw key exactly once (`Cache-Control: no-store`). It is unauthenticated by nature. If `TENANT_CREATION_TOKEN` is set, it requires `x-admin-token` (constant-time comparison); if unset it is open and the server logs a warning at startup. This is a development convenience; a real deployment would put tenant creation behind its own admin auth.
- **Errors:** every error is `{ "error": { "code", "message", "requestId", "details"? } }`. Validation errors list `path` and `message` only. Unexpected errors return a generic 500 with no message or stack; the full error goes to the server log only. A write outside the partition range returns 422 `occurred_at_out_of_range`.
- **Logging:** pino via Fastify with a per-request UUID (`requestId` in every log line, `x-request-id` response header). Logs never include headers or bodies; the server config also redacts `req.headers.authorization` as a second line of defense. A test sends valid, invalid and garbage credentials and asserts none of them (nor `authorization`/`bearer`, nor the key hash) appear in the captured log output.
- **Pagination:** keyset on `(occurred_at DESC, id DESC)` with an opaque base64url cursor carrying microsecond-precision timestamp text (JS dates would truncate to milliseconds and could skip or repeat rows). The query always includes an explicit `tenant_id` predicate in addition to RLS so the planner can use the tenant index.
- **Not included yet:** rate limiting, usage-event idempotency keys, credit debits on ingest (P1.8), API key rotation endpoints.

## D17. Seeding: how it bypasses forced RLS, and its safety limits

- **Options:** (a) run as the compose superuser; (b) a dedicated seeding role with `BYPASSRLS`; (c) run as the app role and set the tenant per statement; (d) add permissive seed-only policies.
- **Choice:** (a): `pnpm seed` connects with `DATABASE_ADMIN_URL` (the compose superuser), which bypasses `FORCE ROW LEVEL SECURITY`.
- **Why:** it needs the least new machinery. (b) would create a standing `BYPASSRLS` role that must then be guarded forever. (c) is impossible for the reset (the app role cannot delete) and awkward for 10M rows across 250 tenants. (d) would put seed-only exceptions in the production policy set, which the isolation tests exist to keep clean.
- **Risks and mitigations:**
  - The seed is a destructive tool. It refuses to run unless the admin URL's host is local (`localhost`, `127.0.0.1`, `::1`) and the database is exactly `ledgerworks`, and unless `--yes` is passed; without `--yes` it prints what it would delete and exits non-zero. These guards are unit-tested (`src/seed/seed.test.ts`). The test database `ledgerline_test` is also refused.
  - It is never reachable from the API: it lives in `src/seed/`, is imported by nothing, and the API process only holds the app-role connection string, not the admin URL.
  - The reset uses `session_replication_role = replica` for a single `TRUNCATE` statement so that the ledger's append-only truncate trigger does not block it, then resets the setting. That is the only place the append-only guard is bypassed, and it needs superuser.
- **Data model (all synthetic):** 250 tenants; usage events per tenant follow a Zipf curve (`share ~ 1 / rank^1.2`), so the largest tenant holds about a quarter of all events and the smallest about 3.4k. Events cover 2025-10-01 to 2026-09-30 (UTC, 12 monthly partitions) with a weekday/weekend pattern, linear growth over the year and a diurnal hourly curve. Everything (ids, timestamps, quantities) is a pure function of the seed value (`md5` of `seed:tenant:month:index`); only API key secrets are random. Generation is set-based: one `INSERT ... SELECT ... generate_series` per month.
- **Credits:** per tenant and month one grant, one debit equal to 1 credit per 100 usage units (computed from the seeded events), and occasional refunds; the balance is the ledger sum, verified after every seed (mismatches must be 0).
- **Keys:** every tenant gets one API key; raw keys for five sample tenants (huge, large, medium, small, tiny) are written to the gitignored `.seed/keys.json` (mode 600) and are never printed.
- **Not tuned:** the seed loads into the tables with their indexes in place and runs plain `ANALYZE` afterwards, no `VACUUM`, no extra indexes, no changed settings, so the data starts in the same state the benchmarks measure.

## D18. Credit debit and refund (P1.8)

- **Options:** (a) a transaction written in the API code; (b) a plpgsql function that runs as the caller (`SECURITY INVOKER`); (c) a `SECURITY DEFINER` function with the app role's direct write privileges on the ledger and balances revoked.
- **Choice:** (b): `ledgerline_fn.debit_credits(amount, key, reference)` and `ledgerline_fn.refund_credits(debit_id, amount, key, reference)`, created in migration 0003.
- **Why:** the logic and the lock live in one place and one round trip, next to the data, instead of being re-implemented by each caller (a). Running as the caller keeps forced RLS and the existing grants in force, with the tenant taken from `app_tenant_id()` and never from a parameter, so a function call cannot touch another tenant (tested). (c) is stronger but would rewrite the privilege matrix and isolation tests; deferred (see risks).
- **Locking:** the first statement is `SELECT ... FROM credit_balances WHERE tenant_id = <current> FOR UPDATE`. All debits and refunds of one tenant serialise on that row; different tenants do not block each other. The balance check, the ledger INSERT and the balance UPDATE then happen in the same transaction. The `CHECK (balance >= 0)` constraint remains as a second line of defence.
- **Idempotency (unique per tenant):** a debit takes a required key. The lookup by key happens after the lock is held, so concurrent requests with one key queue behind the first and then see its committed row. Same key and same amount returns the original result (`replayed = true`, original ledger id and original balance after the debit) and writes nothing. **Same key with a different amount (or a key that belongs to a refund) is rejected with outcome `idempotency_conflict`, not accepted and not applied.** A rejected debit (`insufficient_credits`) writes nothing, so it does not occupy the key; a later retry with the same key is evaluated afresh. Keys share one namespace per tenant across debits and refunds (the existing partial unique index on `(tenant_id, idempotency_key)` is the database-level backstop).
- **Refunds:** a refund references one debit (`refund_of`), is itself idempotent by its own key, can be for any amount from 1 up to the original debit amount, and **a debit can be refunded at most once** (a unique index on `refund_of` backs the function's own check). Repeated partial refunds were deliberately not designed; a second refund of the same debit returns `already_refunded` whatever its amount. A refund is a new ledger row; nothing is ever updated. Outcomes: `refunded`, `debit_not_found` (unknown id, another tenant's debit, or a non-debit row), `refund_exceeds_debit`, `already_refunded`, `idempotency_conflict`.
- **Schema additions (0003):** `credit_ledger.balance_after` and `refund_of`; a composite foreign key `(tenant_id, refund_of) -> (tenant_id, id)` so a refund can only point at the same tenant's row (otherwise one tenant could "refund" another's debit and block it), which needs a unique `(tenant_id, id)`; checks that `refund_of` only appears on refunds and that amounts have the right sign per kind (debit negative, grant and refund positive). The existing seeded rows satisfy all of this (verified by applying 0003 to the seeded database: 0 ledger-vs-balance mismatches). Seeded refund rows are goodwill refunds with no `refund_of`, so seeded debits can still be refunded once through the function.
- **Risks:** (1) the invariant "ledger sum equals balance" holds for everything that goes through these functions; the app role still has direct INSERT on `credit_ledger` and UPDATE on `credit_balances`, so buggy application code could write around them. Revoking those grants and making the functions `SECURITY DEFINER` is the stronger follow-up. (2) Per-tenant serialisation bounds a single tenant's debit rate. (3) The old non-unique index `credit_ledger (tenant_id, id)` is now redundant with the new unique constraint; left in place on purpose (no tuning in this task; logged in `docs/optimization-log.md`).
- **Verification:** `ledgerline/test/credits.test.ts`, real Postgres, 50 separate connections. Mutation check: with `FOR UPDATE` removed from `debit_credits`, the 10,000-debit test failed: all 10,000 debits were accepted and none rejected, 55,225 credits were debited against a supply of 25,000, ledger sums went negative (-30,225 in total against balances of 15,491) and all 5 tenants had a ledger-vs-balance mismatch. With the lock restored, the same test accepts about 4,570 and rejects about 5,430 with no overdraft and no mismatch.

## D19. Job queue (P1.9)

- **Delivery semantics: at-least-once, with at most one live lease per job. Not exactly-once.** A job is claimed with `FOR UPDATE SKIP LOCKED` and leased for a fixed time. If its worker never acknowledges (it crashed, or the handler outlived the lease), the job becomes claimable again once the lease has expired, so a handler can run more than once, for example after a crash that happens after the side effect but before the acknowledgement. Handlers must be idempotent (the credit functions, for instance, take idempotency keys). Acknowledgements are fenced by attempt number and worker id: if a stale worker reports back after its lease was lost and the job re-claimed, `complete_job` returns `false` and `fail_job` returns `stale`, and the newer attempt is untouched. Handler work and the acknowledgement are separate transactions, which is exactly why this is not exactly-once.
- **States:** `queued` (waiting), `running` (leased), `failed` (the last attempt failed, a retry is scheduled at `run_at`; claimable once due), `succeeded`, `dead` (retries exhausted, a `dead_letters` row exists). Every claim writes a `job_attempts` row (`attempt_no`, `worker_id`, start); the acknowledgement or lease expiry closes it with an outcome and error.
- **Claim:** one SQL function, `claim_jobs(worker, queue, limit, lease_ms, now)`: (1) dead-letters jobs whose lease expired with all attempts used (in the same statement as the dead-letter insert), (2) picks runnable rows with `ORDER BY run_at, id LIMIT n FOR UPDATE SKIP LOCKED` (queued or failed and due, or running with an expired lease), (3) closes the previous attempt as `lease expired`, (4) marks them running with a new lease and inserts the new attempt row. No new indexes were added (the existing partial index only covers `status = 'queued'`); the resulting scan cost is logged as an observation, not tuned.
- **Retries:** exponential backoff with jitter, capped, computed by the caller (`retryDelayMs`: base 1 s, factor 2, cap 60 s, "equal jitter": half fixed, half random). Max attempts is per job (default 5). After the last attempt `fail_job` moves the job to `dead` and inserts the `dead_letters` row in the same transaction.
- **Time is injectable:** every function takes `p_now`, and TypeScript code takes a `Clock` (`FakeClock` in tests). Tests do not sleep.
- **Enqueue:** `enqueue_job(...)` with an optional idempotency key, unique per tenant (the existing partial unique index; `INSERT ... ON CONFLICT DO NOTHING` then a lookup). The same key returns the existing job, and the first call's payload wins. Without a key every call creates a new job.
- **RLS design (options):** (a) a worker role with `BYPASSRLS`; (b) workers connect as the app role and the claim is an ordinary function; (c) a narrowly scoped `SECURITY DEFINER` claim function that only a dedicated worker role may execute, with everything else tenant-scoped.
- **Choice: (c).** Workers must claim across tenants, which RLS forbids to the app role, so `claim_jobs` is a `SECURITY DEFINER` function owned by `ledgerline_definer`, executable **only** by a new `ledgerline_worker` login role (no `BYPASSRLS`, no table privileges at all; created by the bootstrap step). A worker process holds two connections pools: the worker role only to claim, and the ordinary app role for everything else. `claim_jobs` returns the tenant id; the handler's database work then runs through `withTenant(job.tenantId)` as the app role, so RLS applies to it, and `complete_job` and `fail_job` are `SECURITY INVOKER` functions that run in that tenant transaction and can only touch that tenant's job. The definer role was extended for this: `SELECT, UPDATE` on `jobs`, `SELECT, INSERT, UPDATE` on `job_attempts`, `INSERT` on `dead_letters`, each with a permissive policy for the definer only (this supersedes the statement in D14 that it has no access to job tables; the isolation tests now assert the exact privilege set).
- **Risks:** (1) whoever holds the worker role's credentials can claim and read the payloads of every tenant's jobs; protect it like a database credential and never give it to the API process. (2) A compromised worker process can run a handler with any tenant id it was handed; the database cannot tell that the id is genuine. (3) `claim_jobs` is a single point where cross-tenant data is visible; it is kept short, pins `search_path`, and returns only the fields a worker needs. (4) A handler that outlives its lease will run concurrently with a re-claim; there is no lease renewal yet.
- **Tests:** `ledgerline/test/queue.test.ts` (failure injection with the backoff schedule checked to the millisecond, dead letters with attempt history, crash and lease-expiry behaviour including fencing of a stale worker, idempotent enqueue, access control) and, at full size, `ledgerline/test/concurrency/queue-10k.test.ts` (50 workers, 10,000 jobs).

## D20. Test organisation: default run versus `pnpm test:concurrency`

- **Problem 1:** test files share one Postgres database and, with Vitest's default of running files in parallel, their connection pools together exceeded `max_connections` (100) once the credit and queue tests existed. `fileParallelism` is only honoured as a global Vitest option, not per project, so both scripts now pass `--fileParallelism=false`.
- **Problem 2:** the full-size queue test (50 workers, 10,000 jobs) takes minutes on the unmodified claim query (see `docs/benchmarks/queue.md`). It lives in `ledgerline/test/concurrency/` and runs through `pnpm test:concurrency`, which sets `CONCURRENCY=1` so the Vitest workspace contains only that project.
- **Not moved:** the 10,000-debit, 50-worker credit test takes about 15 s and stays in the default `pnpm test`.
- **CI:** see the workflow: lint, typecheck and `pnpm test` as before, plus a separate `pnpm test:concurrency` step with its own timeout.

## D21. Ledger invariant hardening: SECURITY DEFINER debit and refund (Step 0 before P1.10)

- **Problem:** D18 chose `SECURITY INVOKER` functions and recorded the gap: the app role still had `INSERT` on `credit_ledger` and `INSERT, UPDATE` on `credit_balances`, so any application code could write around the functions and break "ledger sum equals balance".
- **Options:** (a) keep invoker functions and rely on code review; (b) make the functions `SECURITY DEFINER` owned by the existing `ledgerline_definer`; (c) make them `SECURITY DEFINER` owned by a **new, dedicated** NOLOGIN role `ledgerline_ledger`, and revoke the direct grants from the app role.
- **Choice: (c)** (migration `0005_ledger_invariant.sql`). `ledgerline_definer` already can insert tenants, users and API keys; adding ledger writes to it would make one role the owner of unrelated powers. `ledgerline_ledger` has exactly `SELECT, INSERT` on `credit_ledger` and `SELECT, UPDATE` on `credit_balances`, and nothing else (asserted by tests, including that it has no `DELETE`, no other table and no `BYPASSRLS`).
- **RLS stays in force inside the functions.** The ledger role's policies are tenant-scoped, not permissive: `tenant_id = (SELECT app_tenant_id())` for read, append and balance access. So even a bug inside a function body cannot read or write another tenant's rows, and the tenant still comes from the session setting and never from an argument (the function signatures are unchanged). This is the main difference from the permissive `definer_access` policies of D14.
- **The app role now has `SELECT` only** on `credit_ledger` and `credit_balances`. The old write policies (`tenant_append`, the `FOR ALL` balances policy) were dropped and replaced by a `SELECT` policy, so there is neither a privilege nor a policy to write with.
- **`search_path`:** `pg_catalog, pg_temp`, set on both functions. The bodies were already fully schema-qualified (`public.credit_ledger`, `public.app_tenant_id()`); a test creates temporary tables with the same names, puts `pg_temp` first in the caller's `search_path`, and shows the writes still go to the real tables.
- **The function bodies did not change** (same file `0003`, same mutation target). Only the execution context changed.
- **Seed and tests:** the seed runs as the superuser and is unaffected. Tests that need balances or ledger rows set up fixtures as the admin role.
- **Residual risks:**
  1. **The caller still chooses the tenant by setting `app.tenant_id`.** Whoever can run `set_config('app.tenant_id', ...)` on an app connection can debit that tenant (the function trusts the setting). The database cannot defend against a compromised API process; the API sets the setting only from the authenticated key (D14, D16). This is unchanged, and not made worse.
  2. Any caller holding the app role can spend a tenant's credits through `debit_credits` with a fresh idempotency key. That is the function's purpose; authorisation of the amount is the API's job.
  3. A bug in the two function bodies is now a bug in code that runs with write rights. The mitigations are the tenant-scoped policies above, the pinned `search_path`, the `CHECK (balance >= 0)` and sign constraints, the append-only triggers, and the tests.
  4. `adjustment` and `grant` rows can no longer be created by the app role at all (before, it could insert them directly). There is no API for granting credits yet; when one is added it needs its own definer function.
- **Verification:** `isolation.test.ts` matrix updated (the app role's INSERT and UPDATE on those tables are now privilege-denied in every context), plus tests for the ledger role's exact privileges and tenant-scoped policies; `credits.test.ts` has new tests that the app role cannot insert into the ledger or write balances directly (own tenant, other tenant, no tenant), that tenant A's call cannot affect tenant B even when it passes B's debit id or B's idempotency key, and that `search_path` shadowing does not redirect writes. **Mutation check re-run:** with `FOR UPDATE` removed from `debit_credits`, the 10,000-debit test failed (10,000 accepted, 0 rejected; raw output `docs/benchmarks/raw/mutation-check-row-lock-after-0005.txt`); with the lock, about 4,570 are accepted and about 5,430 rejected. The seeded database was migrated forward (0 mismatches) and then re-seeded from scratch: ledger-sum vs balance mismatches 0, fingerprints identical to the earlier seeds.
- **Supersedes:** the "risks (1)" and the option (c) deferral in D18.

## D22. Job claim indexes (P1.10, E3)

- **Options for O6:** (a) one partial index and leave the query; (b) `UNION ALL` of two index-friendly branches (fresh work and expired leases) merged and limited; (c) two small partial indexes and the same single query restated so the planner can prove the index predicate; (d) claim fresh work first and look at expired leases only when the batch is not full.
- **Choice: (c)** (migration `0006_claim_indexes.sql`). (a) was tried and is a no-op: the old `OR` of different status tests does not let the planner prove the partial-index predicate, so the sequential scan stayed (with `enable_seqscan = off` it produced an unordered BitmapOr that still sorts). (b) cannot lock the rows (`FOR UPDATE` is not allowed on a `UNION`), so selecting candidates first and locking afterwards would make concurrent claimers fight over the same candidates, which defeats `SKIP LOCKED`. (d) changes the ordering (recoveries last, so they could starve). (c) keeps ordering and `SKIP LOCKED` exactly as designed in D19.
- **Invariant relied on:** the pick adds `run_at <= p_now` for running jobs. It is implied for rows that `claim_jobs` itself made running (it only claims jobs with `run_at <= p_now`, and a lease expires after the claim), so the result set is unchanged. A row forced into `running` by hand with a future `run_at` would not be re-claimed until its `run_at` passes; nothing in the code does that and no constraint enforces it. A `CHECK` was not added because it would make the invariant a hard rule for tests and tooling as well.
- **Costs:** about 30% more time for a bulk insert of jobs and 6.9 MB per 110,000 queued jobs for the claim index (`jobs_lease_idx` is tiny). `jobs_runnable_idx` from 0001 is now unused (not dropped here). The indexes are created without `CONCURRENTLY` because migrations run in a transaction; this is only safe because the jobs table is small or empty when the migration runs, and a large live table would need the concurrent variant outside the migration runner.
- **Verification:** queue tests unchanged and passing; the full-size 50-worker, 10,000-job test passes (257 jobs/s, previously about 64); throughput numbers in `docs/optimization-log.md` E3.

## D23. Drop `credit_ledger_tenant_id_idx` (P1.10, E4)

- **Options:** keep both indexes (as D13/D18 left them on purpose); drop the non-unique one; drop the unique constraint's index (impossible: it backs the composite foreign key from D18).
- **Choice:** drop the non-unique `credit_ledger_tenant_id_idx` in migration `0007`. The unique constraint `credit_ledger_tenant_id_id_key (tenant_id, id)` has identical columns and serves the same lookups; `EXPLAIN` shows the planner already used it.
- **Effect (measured, E4):** 4.08 MB less per 100,000 ledger rows; bulk insert about 10 to 34% faster in 5 of 5 paired runs; no measurable change in debit latency. Not claimed as a latency win.

## D24. Automatic partition creation and what partitioning is for (P1.10, E6)

- **Options for creating partitions:** (a) a standing job outside the database; (b) a database function the API calls at startup and on a timer; (c) lazy creation inside the ingest path (catch the error, create, retry); (d) create more years up front (more of what 0001 did).
- **Choice: (b)** (migration `0008`, `src/partitions.ts`). (c) puts DDL with `ACCESS EXCLUSIVE`-level locks on the request path and under the app role; (d) only moves the cliff; (a) needs a second moving part to deploy. The function is idempotent, serialised by an advisory lock, and builds each partition as a standalone table that is then `ATTACH`ed (only `SHARE UPDATE EXCLUSIVE` on the parent), because `CREATE TABLE ... PARTITION OF` blocks all access to the parent. It keeps `PARTITION_MONTHS_AHEAD` (default 6) months ahead, so a failure of the job is visible for months before ingest could be affected; a failed run logs an error and is retried at the next tick.
- **Privileges:** creating a partition needs table ownership, so the function is `SECURITY DEFINER` owned by `ledgerline_owner`. The app role may execute only the variant that uses the database clock, with `p_months_ahead` capped at 24; the variant with an injectable `now` (used by the tests) is not granted to it, so the app role cannot create partitions for months of its choosing. Residual risk: any holder of the app role can cause up to 24 months of empty partitions to exist; they hold no data and are protected like all other partitions (no app privileges, RLS on the parent).
- **What partitioning is for here (measured, E6):** not read speed (the partitioned table was 12 to 24% slower per query than an unpartitioned copy, about 0.03 to 0.06 ms) but retention: dropping a month takes about 25 to 30 ms against 2 to 5 s for the equivalent `DELETE`, with no dead tuples. The decision to partition (D13) stands for that reason, not for query latency.
- **Not done:** automatic _dropping_ of old partitions (retention policy is a product decision); a default partition (which would hide a missing partition by accepting out-of-range data silently); changing 0001's `create_usage_events_partition(date)`, which formats bounds in the session time zone and is correct only because the server runs in UTC.

## D25. How RLS overhead is measured, and why the policies stay as they are (P1.11, E7)

- **Options for a "without RLS" mode:** (a) a flag or code path in the API that skips `set_config` or uses another connection; (b) a throwaway copy of the database with RLS disabled on the tables; (c) a temporary `BYPASSRLS` login role that is a member of the app role, in the same database.
- **Choice: (c)** (`ledgerline/k6/rls-off-role.sh`). (a) is exactly what must never exist: a mode that disables isolation reachable from the application. (b) was tried first and crashed the Postgres container once during the 2.3 GB `CREATE DATABASE ... TEMPLATE` copy (it recovered; the data was verified intact), and it would also have split the cache between two databases. (c) has identical privileges (membership in `ledgerline_app`) and identical data and cache pages, so the only difference is that the policies are not applied. It exists only while the benchmark runs, is reached only by setting `DATABASE_URL` for that process, and is dropped afterwards (the script verifies that no role but the superuser has `BYPASSRLS`). The benchmark script proves which role the API actually connected as (`pg_stat_activity`) before each run. Migrations, policies and the API are untouched.
- **Fairness:** every statement in the API already filters by `tenant_id` explicitly (D16), so the no-RLS mode still filters by tenant and the comparison isolates the policy, not a missing filter.
- **Result (see `docs/benchmarks/rls-overhead.md`):** within the noise end to end; about 0.07 to 0.16 ms (14 to 23%) per transaction at the database level; the tenant setting is evaluated once per statement, not per row.
- **Policy rewrites:** the cheaper variant that keeps exact behaviour saves about 0.014 ms per statement (below the measurement noise); the clearly cheaper one (reading `current_setting` directly) turns a malformed setting into an error, which D15's matrix forbids on purpose ("zero rows, not an error"). So the policies and `app_tenant_id()` stay as designed in D14.
- **Residual risk of the measurement mode:** while the role exists, anyone who knows its (non-secret, development) password can bypass RLS on the local development database. It was created for the benchmark window only and dropped; a production-like environment must never have such a role.

## D26. Partition bounds are UTC everywhere (fix, migration 0009)

- **Problem:** `create_usage_events_partition(date)` from 0001 built its bounds through the session time zone (`date_trunc` on a date, bare date literals in `CREATE TABLE`), so it was correct only because the server runs in UTC. `ensure_usage_events_partitions_at` (0008, D24) used UTC from the start.
- **Fix:** 0009 replaces the function (same signature and result) with bounds computed on `timestamp` values and written as explicit `... 00:00:00+00` literals. Existing partitions are untouched; their bounds were already the UTC month boundaries, and a test now asserts that for every partition of the migrated database.
- **Tests (`ledgerline/test/partitions.test.ts`):** both functions create partitions under session zones UTC, Asia/Kolkata and America/Los_Angeles with identical bounds; events at 23:59:59Z and 00:00:00Z on a month change, inserted under Asia/Kolkata, America/Los_Angeles and Pacific/Auckland sessions, land in the right partitions. Without 0009 the tests fail (checked by removing the migration).

## D27. Observability design (P1.12)

- **Options:** (a) OpenTelemetry auto-instrumentation packages; (b) manual spans with the OpenTelemetry API plus a few small wrappers; Prometheus metrics via `prom-client` served (c) on the API port at `/metrics` or (d) from a separate server.
- **Choice: (b) and (d).** (a) relies on module-loading hooks that are fragile under `tsx` and ESM, and its database spans carry SQL text by default; the wrappers here name spans by operation only and attach exactly the attributes listed in `docs/observability.md`. (c) puts operational data on the public surface; (d) is a separate port and bind address (default loopback) that cannot be reached through the API at all, with an optional bearer token.
- **Cross-tenant queue gauges** need to see all tenants' jobs, which RLS forbids to every normal role. They come from `ledgerline_fn.queue_stats()`, a narrow definer function returning aggregates, executable only by a read-only `ledgerline_metrics` login (also used by Grafana for `pg_stat_statements`). Risks: whoever has that login can read statement texts from `pg_stat_statements` (which can contain literal values only if a client sends them inline; the API uses parameters) and queue counts; it cannot read any table. The Docker profile needs the metrics port bound on all interfaces for Prometheus to reach it: development only.
- **Counters live in the process that does the work** (the API serves HTTP counters, the worker process serves worker and debit counters); Prometheus scrapes both. Queue depth is read from the database at scrape time so it is correct whichever process asks.
- **Not done:** trace/metric correlation (exemplars), alerting rules, a HTTP debit endpoint (so the debit panel is fed by the demo worker), persistent Grafana/Prometheus volumes.

## D28. Admin UI: where it lives, how it authenticates, what it may see (P1.13)

- **Location (options):** the shared `ui/` package (meant for the Ledgerlens plan diagram and Ledgerlatch timeline components) or inside Ledgerline. **Choice: `ledgerline/ui/`** (workspace package `@ledgerworks/ledgerline-ui`, React + Vite + TypeScript). It is an application of this one backend, not a reusable component library; the shared package stays for the later phases.
- **Authentication:** the user types a **tenant API key** into a password-type field. It is held in React state only: never in `localStorage`, `sessionStorage`, a cookie or the URL, never rendered into the page, and reloading signs out (tested in jsdom and in a real browser). The UI sends it as `Authorization: Bearer` on same-origin requests (`credentials: 'omit'`, `cache: 'no-store'`). There is **no CORS**: in dev and preview the Vite server proxies `/api` to the API, and a deployment would serve the UI and the API from one origin.
- **Data it needs:** usage over time, ledger entries and queue health for the caller's tenant. The existing endpoints did not provide them, so three **tenant-scoped** read endpoints were added, all behind the same API-key auth, with strict query schemas and an explicit `tenant_id` filter on top of RLS: `GET /v1/usage/summary` (daily totals in UTC, at most 92 days), `GET /v1/credits/ledger` (keyset-paginated, newest first), `GET /v1/queue/stats` (counts by state, age of the oldest waiting job, last 10 dead letters with the error truncated to 200 characters). Tests: 401 for every one of them in the auth matrix, validation errors, pagination, and a two-tenant test that each tenant sees only its own rows on all three endpoints, in both directions; the underlying tables are already in the isolation matrix.
- **What the UI must not do:** show **global, cross-tenant** operational views. Those exist only in Grafana (D27) behind its own access. No endpoint returns another tenant's data or a cross-tenant aggregate.
- **Risks:** (1) a raw API key typed into a browser is exposed to anything that runs in that page (a browser extension, an XSS bug); memory-only storage limits persistence, not exposure. A stricter design would be short-lived session tokens minted from the key, which does not exist yet. (2) A dead letter's error text is shown to the tenant (truncated): handlers must not put secrets in error messages. (3) Anyone with a key can load the usage summary for up to 92 days, which scans that tenant's events in the range (measured cost is not part of this task); the cap bounds it. (4) The ledger endpoint shows the `reference` text the tenant's own code wrote.
- **Accessibility:** every panel has loading, empty, error (with retry) and unauthorized states, each with text and a symbol (never colour alone) and a live region; the chart is an image with a text alternative plus a data table; amounts carry a sign and a text hint.
- **Tests:** 20 component tests (Vitest, Testing Library, jsdom) cover all states of all panels, key handling and sign-out; 4 Playwright tests in `e2e/` run a real browser against the real API and database: displayed numbers equal a direct API call for the huge and the small tenant, tenant A's key never shows tenant B's ledger ids (both directions), and a wrong key shows unauthorized and leaves nothing in storage. CI runs them against a small deterministic demo seed (`pnpm seed:demo`, about a second) instead of the 10M-row seed.

## D30. How the shadow is cloned: schema dump plus COPY streaming (C2.1)

- **Options:** (a) `pg_dump -Fc | pg_restore -j` of schema and data; (b) a schema-only `pg_dump` (restored in sections) plus `COPY ... TO STDOUT | COPY ... FROM STDIN` of the data; (c) a physical copy (`pg_basebackup`); (d) `CREATE DATABASE ... TEMPLATE` on the source server.
- **Choice: (b).** (c) needs a replication role and copies the whole cluster, so it cannot run under a read-only role. (d) runs inside the source container (more load on it, and it crashed that container once for the 2.3 GB copy, D25) and cannot sample. (a) cannot filter rows, so a sampled copy would need a second method; (b) gives one path for both modes.
- **How it works:** one source session exports a snapshot (`REPEATABLE READ`, `pg_export_snapshot()`); `pg_dump --schema-only -Fc --snapshot=...` (run inside the shadow container, version 16 client) and every COPY worker (`SET TRANSACTION SNAPSHOT`) see exactly that state. `pg_restore --section=pre-data` creates tables, partitions, types, functions, owners and grants; the data is streamed into the leaf tables (each partition on its own, largest first, `FROM ONLY`) before any index or constraint exists; `pg_restore --section=post-data -j` then builds indexes, primary and foreign keys, triggers, RLS (`ENABLE`/`FORCE`) and policies in parallel. Because constraints are created after loading, foreign keys are **validated by the database**, so a sampling rule that cannot keep integrity fails the clone instead of producing orphans. The source snapshot is released before the index builds, so the long source transaction lasts only as long as the data copy.
- **What is preserved (compared by `schemaSnapshot`; 870 lines on the small demo database and 873 on the 10M-row one, 0 differences in both):** tables, partitions and their bounds, columns (types, defaults, identity, generated), indexes, constraints, sequences (definition and current value, set with `setval`), policies, RLS flags, triggers, functions (body hash, owner, ACL), views, enums, extensions. Materialized views are refreshed after loading.
- **Roles and ownership (decision):** ownership and grants are kept as in the source (no `--no-owner`), because the owner of a `SECURITY DEFINER` function decides whose privileges and RLS exemption its body runs with; re-owning everything to the shadow administrator would change both. So every non-system source role is created in the shadow as `NOLOGIN`, with **no password and never `SUPERUSER`** (a source superuser is recorded as `wasSuperuser` in the manifest), keeping `BYPASSRLS`, `CREATEDB`, `CREATEROLE`, `INHERIT`, the memberships between those roles, and the `ALTER ROLE/DATABASE ... SET` settings (except `default_transaction_read_only`). Experiments can `SET ROLE ledgerline_app` to measure under RLS; nobody can log in as the copies.
- **Extensions:** the clone refuses (before copying) when the source uses an extension that the image cannot provide.
- **Settings:** the planner-only settings (cost parameters, `effective_cache_size`, `work_mem`, `default_statistics_target`, `jit`, parallelism) are copied from the source so plans are comparable; memory-allocating settings follow the shadow's own limit (`shared_buffers` 25% of its memory). Both sides are listed in the manifest (`settings`); for Ledgerline the shadow has `shared_buffers` 768 MB against 512 MB at the source and `max_wal_size` 2 GB against 1 GB. Those differences are real and later timing comparisons must say so.
- **Costs and limits:** an extra `count(*)` pass over each table on the source (needed for exact ratios); `pg_dump` resets `statement_timeout` for itself, so only the process timeout bounds it (it reads the catalogs only). **Not copied:** large objects, foreign tables' data, publications and subscriptions, extension-owned tables (they come from `CREATE EXTENSION`).
- **Measured (full clone of the 10M-row seed, 2 CPUs / 3 GiB shadow, 2 copy streams):** see `docs/benchmarks/shadow-clone.md`.

## D31. How the source is protected (C2.1)

- **The role:** `provisionReaderRole` (run once by an administrator; the runner never creates roles on the source) makes a login role with `pg_read_all_data`, `BYPASSRLS`, `default_transaction_read_only = on`, and no superuser, `CREATEDB`, `CREATEROLE` or `REPLICATION`. `BYPASSRLS` is required: Ledgerline's tables have `FORCE ROW LEVEL SECURITY`, and a role subject to the policies would copy zero rows without any error. The runner therefore refuses a role that is subject to RLS on any RLS-enabled table (tested), and its data sessions set `row_security = off`, which turns a would-be silent filter into an error, as `pg_dump` does.
- **Every source session** gets, at connection start (server-enforced): `default_transaction_read_only = on`, `statement_timeout` (30 min for the COPY sessions, 60 s for catalog reads), `lock_timeout` 10 s (`pg_dump --lock-wait-timeout=10000`), and an `application_name` (`ledgerworks-shadow-<run>`) so an operator can see and cancel it. It verifies the setting took effect. In addition every statement sent through `SourceSession` must pass an allow-list (`SELECT`, `WITH`, `SHOW`, `SET`, `BEGIN/ROLLBACK`, `COPY (SELECT ...) TO`, no write keyword, no `nextval`/`setval`, no row locks); the unit tests cover it. There is no code path that sends DDL or DML to the source.
- **The readiness check (`checkSourceReadOnly`)** does not trust the session default. In a throwaway transaction it switches to `READ WRITE`, takes a privilege inventory (superuser, `CREATEROLE`/`CREATEDB`/`REPLICATION`, table and sequence privileges, `CREATE` on schemas and the database, membership of `pg_write_all_data`, `pg_execute_server_program`, `pg_write_server_files`), then tries a `CREATE SCHEMA` and a no-row `DELETE` and rolls everything back. `createShadow` refuses a role that can write (`SourceWritableError`), unless `allowWritableSource` is set: that is logged with `!!! OVERRIDE`, stored in the manifest (`readOnlyCheck.overrideUsed`, plus a warning) and the runner still only reads.
- **A cost of the probe that matters for the proof of "no writes":** for a role that _can_ write, the probe really executes the `CREATE SCHEMA` and `DELETE` before rolling back, and `pg_stat_database` counts rolled-back catalog tuples. So only runs with a writable role (the override) move the counters; the read-only role's probes are denied and write nothing. The "source unchanged" test therefore runs before the tests that use the administrator role on the source (found while writing it).
- **Impact on the source while cloning:** two copy connections by default plus the snapshot holder; an optional cap on MB/s (`maxSourceMBps`, not used in the measured runs); the snapshot transaction is released before the index builds. Measured for the 10M-row clone: the source container was not OOM-killed, not restarted, and peaked at 1,128 MiB of its 2 GiB (docker stats, sampled every few seconds). The source container's I/O cannot be isolated from the shadow's on Docker Desktop (one VM, one disk); the shadow's CPU and memory are capped, its I/O is not.
- **Proof the source is unchanged:** `sourceFingerprint` (exact row counts of every table, md5 of every small table, `pg_stat_database` and `pg_stat_user_tables` write counters) before and after; identical in the small suite (58 tables, three successful clones, one sampled clone, and four failed or killed ones in between) and for the 10M-row clone.
- **Bugs this found:** a copy worker leaked its source session when the shadow container died before the worker's destination connected (the failure test caught it; fixed, and the test now checks `pg_stat_activity` for leftover sessions).

## D32. Sampling rule (C2.1)

- **Rule:** a root table (for Ledgerline `public.tenants`) is sampled by a deterministic hash of its primary key (`hashtextextended(key::text, seed)`), so the same seed always selects the same rows. A table with a foreign key into the sampled set keeps exactly the rows whose referenced row is kept, for every such key (whole parents with all their children, through any number of levels; a table with two sampled parents needs both). A table that is only _referenced_ by kept rows (`users`, through `memberships`) keeps just the rows that are referenced (`uncovered: 'referenced'`, or `'full'` / `'empty'`). A table with no foreign-key link at all (`schema_migrations`) follows `isolated` (default: copy it completely), and `fullTables` forces whole tables. Self-references are not followed; the foreign keys are validated when they are created, so a rule that cannot keep integrity fails loudly.
- **The ratio is a ratio of root rows, not of data.** With a skewed tenant size distribution the data ratio can differ a lot from it: for Ledgerline, `ratio: 0.1` with seed 20251001 kept 22 of 250 tenants (8.8%) but only **289,749 of 10,000,000** usage events (**2.9%**), because the kept tenants happen to be small (Zipf, D17). That is why every manifest lists the actual per-table ratios and a `scaling` block (`totalRowRatio`, `largestTableRatio`, and a note) that any later report must carry: timings, plan shapes and sizes measured on a sample are not full-scale. Choosing the seed to hit a target data ratio is possible (the predicates can be counted on the source) but is not automated.
- **Statistics:** `ANALYZE` runs on the shadow after loading, so planner statistics describe the sample, not the source. A plan on a sample can differ from the plan on the full data (the planner chooses by row counts), not just run faster; sampled shadows are for correctness and shape checks, full shadows for timings.

## D33. Marker, lifecycle and resource limits (C2.1)

- **Marker (what C2.2 checks):** a database-level setting `ledgerworks.shadow_run_id` (`ALTER DATABASE ... SET`) **and** a row in `ledgerworks_meta.shadow_marker` with the same run id **and** the full manifest in that row; all three must agree (`assertShadow`, throws `NotShadowError`). The marker is written last, so a half-finished clone is never recognised as a shadow. The container and volume carry the labels `ledgerworks.shadow=true`, `ledgerworks.shadow.run-id`, `ledgerworks.shadow.created-at`, `ledgerworks.shadow.mode`. This is a guard against mistakes, not against someone who wants to forge a marker: anyone who can write to a database can add one.
- **Names and cleanup:** container `lw-shadow-<run8>`, volume `lw-shadow-<run8>-data`, a volume of its own (never the source's). `cleanupShadows` considers only resources that have the label **and** the name prefix; resources older than the given age are removed (containers first, then volumes, including volumes whose container is gone); `dryRun` removes nothing. Tests cover: an unlabelled container and volume with the prefix, a labelled container with another name, and a shadow younger than the age; none are touched. Failure inside `createShadow` removes the container and volume (also when the container was killed in the middle of the copy, tested); `withShadow` tears down in `finally`. A killed process leaves resources behind: `shadow cleanup` is the answer.
- **Resources:** the shadow container has its own `--cpus` (default 2), `--memory` and `--memory-swap` (default 3 GiB, no swap), `--shm-size`, `--pids-limit`, listens on `127.0.0.1` only, and runs on its own volume. Before starting, the runner reads the Docker host's CPUs and memory and **refuses** if the shadow plus a reserve for the source (default 2 CPUs, 2 GiB, plus 1 GiB for the VM) does not fit; this is meant for the case where the source runs on the same host. **What was verified:** the full clone of the 10M-row database at 2 CPUs / 3 GiB on a Docker host with 8 CPUs / 9.6 GiB while the source ran with its own 2 CPUs / 2 GiB. **What was not:** anything smaller, so the minimum is not known; the cgroup peak of the shadow reached its 3 GiB limit (page cache from writing 2.3 GB, which the kernel reclaims; the sampled working-set peak was 1,739 MiB, polled every few seconds so it can miss short peaks). I would not go below 2 GiB without testing.
- **The shadow's password** is random per shadow, passed to Docker through the environment (never on a command line), kept in memory by the handle and in the container's environment (so `attachShadow` and `shadow url` can find it: anyone with access to the Docker socket can read it, as they can anyway read the data). It never appears in a manifest, a log or an error message (tested with a wrong source password and a scan of the manifest).

## D34. Measurement harness: what one measurement is, and how writes and DDL are made safe (C2.2)

- **What a query measurement is.** Per measured run the statement is executed twice: once as written, timed by the client's wall clock (so no EXPLAIN overhead in it), and once as `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`, which supplies the server-side execution time, planning time, the plan and the buffer counts. Reported: p50, p95, min, max, sample standard deviation and CV for both clocks, rows returned (or affected), the full plan JSON of the **first** and of the **median** run (median by server execution time; lower median for an even count), the buffer hit/read counts of the median run, and every run's numbers. Percentiles use linear interpolation between ranks (numpy's default); with 20 runs, p95 interpolates between the 19th and 20th value. Wall time is larger than server time by planning, the network round trip and result transfer (for the fast usage-read on the small shadow: 3.1 ms wall against 0.26 ms server).
- **Strategy by statement class** (`classifyStatement`, tested): a **read** runs in `BEGIN READ ONLY ... ROLLBACK`, so a function that writes (`nextval`) fails instead of writing (tested: SQLSTATE 25006). **INSERT/UPDATE/DELETE/MERGE** (and `WITH` containing one, `SELECT ... FOR UPDATE`, `EXPLAIN`, `CALL`, `DO`) run inside `BEGIN ... ROLLBACK`: EXPLAIN ANALYZE really executes them. **DDL** is transactional in PostgreSQL and also runs inside `BEGIN ... ROLLBACK`. **CREATE/DROP INDEX CONCURRENTLY, REINDEX ... CONCURRENTLY, VACUUM, CREATE/DROP DATABASE, ALTER SYSTEM, tablespaces** cannot run in a transaction block, so they cannot be rolled back: the caller supplies a `freshShadow` provider and **every run gets its own fresh shadow** (destroyed afterwards); without one the result is the typed failure `needs-fresh-shadow`. A cheaper provider (`CREATE DATABASE ... TEMPLATE` inside the shadow) is possible but not built.
- **What rollback does not undo (honest list).** (1) Sequence values consumed. (2) **Physical dead space:** a rolled-back INSERT or UPDATE leaves dead tuples and extended heap pages until `VACUUM`, so after DML measurements a table's _size_ can be larger than before while its _rows_ are unchanged; the write test therefore compares row counts and an md5 of every row (identical before and after), not sizes. (3) Statistics counters (`pg_stat_*` count rolled-back work). (4) Anything outside the database that a trigger or function does. For DDL the harness checks that rollback restored the table: the file (relfilenode), the indexes and the sizes after `ROLLBACK` equal those before (`verification.rolledBackCleanly`, true in every transactional test).
- **DDL fields** (the contract for Ledgerlatch, `version` 1 in `schema.ts`): `durationMs` and `lockWaitMs` (stats over the runs), `locks.held` (relation, kind, lock type, mode, granted), `locks.targetTableModes` (strongest first) and `strongestTargetTableMode`, `blocksSelects` / `blocksWrites` (derived from the lock conflict table: only ACCESS EXCLUSIVE blocks a plain SELECT; SHARE and stronger block INSERT/UPDATE/DELETE), `rewrite.tableRewritten` (the table's `relfilenode` changed; for a partitioned table, per partition), `rewrite.indexesRebuilt` / `indexesCreated` / `indexesDropped`, `toastRewritten`, `size.before` / `size.after` / `deltaBytes` (table, indexes, TOAST, total, by `pg_relation_size`), `verification.rolledBackCleanly`.
- **How locks are captured.** For a transactional statement the lock list is read from `pg_locks` for the session **right after the statement, inside the transaction**: a transaction holds every lock it took until it ends, so nothing is missed. For a non-transactional statement locks are released between phases, so the list comes from **sampling** `pg_locks` from a second session while the statement runs (`locks.source` says which). Lock _wait_ time is also sampled (`pg_stat_activity.wait_event_type = 'Lock'`): it is an estimate whose error is about one sampling interval, and **the interval is about 15 ms on this Windows machine** (timer resolution; reported as `config.samplingIntervalMs`). Tested: a second session holding `ACCESS SHARE` for 800 ms made `ADD COLUMN` report a lock wait of 801 ms (median of 3); without the blocker, 0 ms. `blockingTransaction` (a lock another session holds for N ms) is an option of `measureDdl`, which is also how Ledgerlatch will simulate a long-running transaction.
- **Cold versus warm.** `cache.mode: 'warm'` runs the warmup first. `'cold-ish'` restarts the shadow's Postgres before **every** run (empties `shared_buffers`; the shadow's host port is fixed so it keeps its address) and measures one `EXPLAIN (ANALYZE)` execution per sample (a second execution would find the cache filled, so in this mode `wallMs` includes EXPLAIN overhead). With `dropOsCache` it also drops the page cache of the Linux kernel that runs the container (on Docker Desktop: the VM) through a privileged helper container, and reports `droppedOsCache` only if that worked. The result's `cache.claim` is one of `warm-after-warmup`, `shared-buffers-emptied-os-cache-warm` or `shared-buffers-emptied-vm-page-cache-dropped`; **nothing here is called a true cold cache**: caches below the VM (the Windows host, the SSD) are not controlled, and without the drop the blocks reported as "read" probably came from the kernel's cache. `track_io_timing` is switched on for the session so `buffers.ioReadMs` shows how long those reads took, which separates "from the OS cache" from "from disk". Observed on the small shadow (median server time): warm 8.7 ms with 0 blocks read; after a restart 9.8 ms with 427 blocks read and 2.1 ms of read time; with the VM page cache dropped as well 12.4 ms and 5.6 ms of read time.
- **Safety nets.** Every statement has a server-side `statement_timeout` (default 30 s; never beyond what is left of `maxTotalRuntimeMs`), `lock_timeout`, and a client-side watchdog (timeout plus 3 s) that drops the connection if the server does not answer; a `docker pause` of the shadow in the middle of a statement returned `client-watchdog` after 4.07 s. The total runtime is bounded (`max-runtime-exceeded`, with the number of completed runs). All failures are **returned** as a typed result (`status: 'failed'`, `failure.kind` one of `refused-not-shadow`, `invalid-input`, `connection-error`, `sql-error` with the SQLSTATE, `statement-timeout`, `lock-timeout`, `max-runtime-exceeded`, `client-watchdog`, `needs-fresh-shadow`), never thrown and never a hang.
- **Refusing non-shadows.** The first thing a session does after connecting is `assertShadow` (D33): marker setting, marker table and manifest must agree; otherwise `refused-not-shadow` and the statement is never sent (tested against the Ledgerline source, a database with a half-built marker, and a plain database). The **only** way around it is `internal-testing.ts`: not exported from any `index.ts`, not part of any option schema (the option schemas are strict, so `{ skipShadowCheck: true }` or `{ cache: { skipShadowCheck: true } }` are rejected as invalid input), it throws unless `VITEST` and `LEDGERWORKS_ALLOW_NON_SHADOW_FOR_TESTS=1` are both set, it logs a line of `!!!!!!!!` on every call, and the result it returns carries `shadow.manifestId = "UNVERIFIED-NOT-A-SHADOW"`. **Rule for the later phases:** no tool definition or MCP schema may expose anything like it; a test checks that the public API has no such name.
- **Is the database quiet?** Every measurement records `environment.background`: autovacuum workers running at its start and end, autovacuum/autoanalyze runs that finished during it, and checkpoints that started during it, with `quiet` true only if all of those are zero; `summarizeQuery` / `summarizeDdl` lead with `!! NOT QUIET` otherwise. A test forces a `CHECKPOINT` in the middle of a measurement and sees it. `settleShadow` (waits for running autovacuum, then `VACUUM (ANALYZE)` and `CHECKPOINT`; refuses anything that is not a verified shadow) is how a shadow is made quiet. Why: see D36, the first measurements after a clone were disturbed by autovacuum for about 2.5 minutes. **Superseded by D37:** `createShadow` now settles by default.
- **Result format.** `QueryMeasurement` and `DdlMeasurement` are zod discriminated unions on `status` (`ok` / `failed`) with `version: 1`, and carry a `shadow` block (manifest id, `sampled`, row ratios and the scaling note) so a report built on them can print the warning; `summarizeQuery` / `summarizeDdl` print a human-readable summary that leads with a loud line when the shadow was sampled.
- **Not done:** no automatic choice of warmup count, no outlier removal (all runs are kept), no concurrent-load measurement (one session), no measurement of `EXPLAIN` without `ANALYZE`, no per-run lock capture for CONCURRENTLY statements beyond sampling.

## D35. DDL behaviour observed against PostgreSQL's documented behaviour (C2.2)

Measured on the small shadow (PostgreSQL 16.15, a 200,000-row table with a primary key and one secondary index, 2 runs each, every run rolled back; test `4.` in `core/src/harness/harness.test.ts`, raw results in `docs/benchmarks/raw/c2.2-small-harness-results-20261003T053846Z.json`):

| Statement                                                                | Lock modes held on the table       | Rewritten                  | Indexes rebuilt          | Duration (p50) |
| ------------------------------------------------------------------------ | ---------------------------------- | -------------------------- | ------------------------ | -------------- |
| `CREATE INDEX ... (c)`                                                   | ShareLock                          | no                         | no (1 created, +1.4 MiB) | 137 ms         |
| `ADD COLUMN e1 int DEFAULT 5`                                            | AccessExclusiveLock                | **no**                     | no                       | 1.1 ms         |
| `ADD COLUMN e2 timestamptz DEFAULT now()`                                | AccessExclusiveLock                | **no** (`now()` is STABLE) | no                       | 1.2 ms         |
| `ADD COLUMN e3 double precision NOT NULL DEFAULT random()`               | AccessExclusiveLock, ShareLock     | **yes** (volatile default) | yes                      | 428 ms         |
| `ADD COLUMN e4 uuid DEFAULT gen_random_uuid()`                           | AccessExclusiveLock, ShareLock     | **yes**                    | yes                      | 895 ms         |
| `ALTER COLUMN a TYPE bigint` (indexed)                                   | AccessExclusiveLock, ShareLock     | **yes**                    | yes                      | 584 ms         |
| `ALTER COLUMN c TYPE varchar(40)` (from `varchar(20)`)                   | AccessExclusiveLock                | **no**                     | no                       | 1.0 ms         |
| `ALTER COLUMN b SET NOT NULL`                                            | AccessExclusiveLock                | no (full scan)             | no                       | 17 ms          |
| `ADD CONSTRAINT ... CHECK (a >= 0) NOT VALID`                            | AccessExclusiveLock                | no                         | no                       | 1.5 ms         |
| `CREATE INDEX CONCURRENTLY ... (d)` (fresh shadow per run, 300,000 rows) | ShareUpdateExclusiveLock (sampled) | no                         | no (1 created, +2.8 MiB) | 457 ms         |

- **Everything matches the documented behaviour:** the constant default does not rewrite (PostgreSQL 11 and later), a volatile default does, a STABLE default does not, a type change between `int` and `bigint` does, widening a `varchar` does not, `SET NOT NULL` scans without rewriting, `CREATE INDEX` takes `SHARE` (blocks writes, allows reads), `CREATE INDEX CONCURRENTLY` takes only `SHARE UPDATE EXCLUSIVE` (blocks neither).
- **One detail worth knowing, not a contradiction:** the rewriting statements also show a `ShareLock` on the table besides `AccessExclusiveLock`. It comes from the index rebuild that follows the rewrite (`reindex`), which asks for `SHARE` on the heap; the strongest mode is what decides who is blocked, and that is `AccessExclusiveLock`.
- **Durations of the fast statements (1 to 2 ms) are metadata-only changes** and say nothing about how long they hold the lock under load: the lock itself is what Ledgerlatch must judge, not the duration, and a statement that waits for a long-running transaction waits first (see the lock-wait test).
- **Sizes:** the rewriting statements grew the table by 1.9 MB (`e3`, and `a` to bigint; about 9 bytes more per row) and 4.0 MB (`e4`, about 20 bytes more per row). These are sizes of the new file, measured inside the transaction before it is rolled back.

## D36. Run-to-run variance of the harness, and what difference counts as real (C2.2)

- **Experiment:** `pnpm --filter @ledgerworks/core variance` (`core/src/harness/variance-cli.ts`). Five cases on a **full** shadow of the 10M-row synthetic Ledgerline database (2 CPUs / 3 GiB container, settled with `settleShadow`, `shared_buffers` 768 MB, planner settings copied from the source), each run **10 times** as a complete `measureQuery` / `measureDdl` with its own warmup (3) and 20 measured runs (DDL: 3 runs per repetition). Raw: one file per case and experiment in `docs/benchmarks/raw/c2.2-variance-<case>-<label>-<time>.json` (every repetition with every run, plan and the machine description); all tables are in `docs/benchmarks/c2.2-variance.md`.
- **Machine:** Intel Core i5-1135G7 (4 cores / 8 threads, 19.8 GB RAM), Windows 11, Docker Desktop VM with 8 CPUs / 9.6 GiB. **It is a developer laptop, not a dedicated benchmark machine:** the script started nothing else, but other applications and Windows itself were running and the CPU frequency is not fixed. That is the likely main source of the noise below, and it was not controlled.
- **Result of the final experiment** (each repetition's p50 of the wall clock; the mean and spread of those ten p50s):

| Case                                                                   | mean of p50 | range of the 10 p50s | CV of p50 across repetitions | (max-min)/mean | CV of the 20 runs inside one repetition (mean) |
| ---------------------------------------------------------------------- | ----------- | -------------------- | ---------------------------- | -------------- | ---------------------------------------------- |
| usage-read after the E1 fix (index scan, top 51)                       | 1.26 ms     | 1.12 to 1.77 ms      | **15.0%**                    | 51.6%          | 17.5%                                          |
| usage-read before the E1 fix (sorts 64k rows)                          | 53.0 ms     | 44.2 to 66.7 ms      | 11.5%                        | 42.3%          | 28.7%                                          |
| usage aggregate over one month (about 270k rows)                       | 87.2 ms     | 82.7 to 92.5 ms      | 3.7%                         | 11.2%          | 23.4%                                          |
| UPDATE of one balance row (rolled back)                                | 0.98 ms     | 0.84 to 1.26 ms      | 11.7%                        | 43.3%          | 21.7%                                          |
| DDL: ADD COLUMN NOT NULL DEFAULT random() (200,000-row table, rewrite) | 282 ms      | 249 to 330 ms        | 9.6%                         | 28.8%          | 11.4%                                          |

- **A coefficient of variation above 15% is reported, as required.** A single run is not trustworthy: the CV of the 20 runs inside a repetition is 17% to 29% on average for every query case (the median of 20 is what is stable). The sub-2 ms usage-read is at **15.0%** across repetitions in the final experiment (borderline), was **17.1%** in the first experiment, **50.2%** in one pinned experiment, and the credit update reached **22.0%** in one long experiment. The server-side time (EXPLAIN) of the cheap statements is steadier than the wall clock (CV of p50 3% to 18%).
- **What I tried to reduce it, and what it showed** (same shadow throughout; the `cpuset` field in the raw files is the truth, the labels were typed by hand):
  1. **Settle the shadow first (kept: `settleShadow`, run by the CLI).** The first experiment ran right after the clone and overlapped autovacuum of the freshly loaded partitions (`last_autovacuum` of the 12 partitions falls between 04:54:00 and 04:56:03 UTC; the measurements started at about 04:55). Settled, the same case went from CV 17.1% to 6.9% and 8.0% (two runs), and the DDL case from 518 ms to about 290 ms (its scratch table needed the same treatment). This is the one change that clearly helped.
  2. **CPU pinning** (`docker update --cpuset-cpus 2,3`, same 2-CPU quota; recorded in the raw files; applied only to this throwaway shadow): usage-read CV 50.2%, 14.2%, 5.7%, 6.7% in four pinned experiments against 6.9%, 8.0%, 15.1%, 15.0% unpinned; credit update 5.5%, 6.8%, 5.6%, 7.7% against 7.2%, 12.4%, 22.0%, 11.7%. Pinned looks slightly steadier, but one pinned experiment was the worst of all and the difference is inside the experiment-to-experiment scatter, so it is **inconclusive and not adopted**. A first attempt to undo the pin with `--cpuset-cpus ""` did nothing; the experiments after it that are labelled "unpinned" but show `2,3` in the cpuset column were in fact pinned, and the real unpinned ones use `0-7` (all CPUs of the VM).
  3. **More runs per repetition** (10 warmup + 100 measured): CV 14.2% and 5.7% pinned, 15.1% unpinned, credit update 22.0% unpinned: **no improvement**; a longer repetition just sees more of whatever the laptop does.
  4. **`shared_buffers` fixed** (it already was, 768 MB) and **nothing else started by the script**. The machine itself was not quieted (no applications closed, no fixed CPU frequency): I did not try that.
- **The finding that matters more than the CV:** the median of the same query moves between experiments run minutes apart by more than the CV inside one experiment. The before-E1 query had a mean p50 of 72.1 ms (while autovacuum ran), 65.6 ms and 53.0 ms in three consecutive experiments (the last two settled); the after-E1 query 1.26 to 1.67 ms unpinned. So numbers from different sessions cannot be compared at the precision a CV suggests.
- **What difference counts as real (a rule of thumb from these data, not a statistical test):**
  - **Compare A and B in the same session, interleaved, with several repetitions each** (the fast-versus-slow test does: two repetitions of each; the ratios were 9.7 and 10.1 by wall clock and 112 and 114 by server time). Do not compare against a number taken earlier.
  - For a query of **50 ms or more**: the observed (max-min)/mean over ten repetitions was 11% to 42%, so call a difference real only if it is **larger than about 40%**, or if the ranges of at least three repetitions of each side do not overlap.
  - For a query under **2 ms**: observed spread 18% to 52% (up to 124% in a disturbed experiment). The wall time is dominated by planning, the round trip and the container's port proxy, so use the server time, and call a difference real only if it is **a factor of 2 or more**.
  - For **DDL durations** (rewrite of a 200,000-row table): spread 24% to 36%; call a difference real above **about 50%**. Lock modes and rewrite flags are deterministic and need no such margin (every repetition agreed).
  - A measurement the harness flags `quiet: false` should be repeated after `settleShadow`.
- **Not done:** a dedicated or frequency-pinned machine; Linux (the port proxy and timers behave differently, so these numbers describe this laptop only); more repetitions (with 10, the CV estimate itself is uncertain by about a quarter of its value, visible in the repeat runs: 6.9% and 8.0%, 7.2% and 12.4% for identical settings).

## D38. LLM interface and OpenAI-compatible adapter (C2.3, C2.4)

- **No vendor SDK; plain `fetch`; the OpenAI chat-completions format first.** The adapter takes a `fetch`-shaped function, so the safe fetch of C2.7 plugs in without changes, and a `Clock` and a random function so tests do not sleep. All automated tests use `FakeProvider` or a local mock HTTP server on `127.0.0.1`; a real provider is only ever reached by the manual `pnpm llm:smoke` (keys from environment variables only). **No claim about model quality is made anywhere**: the tests check the code's handling of what a server sends, not what any model would do.
- **Everything from the server is untrusted.** Responses are size-limited and parsed defensively; a malformed body, chunk or tool call is an `invalid_response` (or a flagged `argumentsError`), never an exception that escapes. Errors carry no request body, headers or response body, and their messages go through redaction with the configured key.
- **Streams do not throw provider errors:** a failed stream ends with an `error` event; `chat()` throws `LLMError`. Both are cancellable with an `AbortSignal`.
- **Decision on malformed tool arguments:** the adapter does not reject a tool call whose arguments are not valid JSON; it passes it on with `argumentsError` and the raw text, so the agent loop (D39) can offer its single repair attempt. What cannot be turned into a tool call at all (no name, duplicate ids, `finish_reason: tool_calls` with nothing to read) is `invalid_response`.
- **Text tool calls are recognised conservatively** (the whole reply must have the exact shape and name an offered tool) and flagged. The risk: a model that legitimately answers with exactly such a JSON object would be read as a tool call; the alternative, never recognising them, makes such servers unusable. The flag `text_tool_call` makes it visible in results and traces.
- **Retry rules:** 429, 5xx and network errors, exponential backoff with full jitter, `Retry-After` as a floor, a sleeping budget; no retry of timeouts (the caller's timeout is already the budget), of other 4xx, of an exhausted quota, or after a stream has delivered content. In-body failures of a stream are typed mid-stream errors, not retried.
- **Not done:** no automatic retry of a stream that failed after the headers but before any content (it surfaces as an error), no support for non-OpenAI wire formats, no embeddings or images, no token counting beyond the 4-characters-per-token estimate that is labelled as such. `pnpm llm:smoke` was **not run** (no key in the environment).

## D39. The agent loop (C2.5)

- **Validation library: zod** (already a dependency of `core`; v4 can derive the JSON Schema that is offered to the model from the same schema with `z.toJSONSchema`, so there is one source of truth per tool). Rejected: ajv, which would need a second schema language next to zod. Limitation: a tool whose schema arrives as raw JSON Schema (for example from a third-party MCP server, later) needs a small adapter or ajv; not built.
- **Loop contract.** `runAgent` never throws for provider failures, cancellation or limits: it returns a typed `stopReason` (`final_answer`, `step_limit`, `token_budget`, `wall_clock`, `cancelled`, `provider_error` with the LLMError kind and `retryAfterMs`, `tool_failure`, `capability_unsupported`). The step limit counts model calls; the token budget uses provider-reported usage (estimates are flagged in the totals) and is checked before each model call; the wall clock also aborts a model call or a tool that is in flight. A 429 is first handled by the adapter's retry and backoff; when its budget is spent it surfaces as `provider_error` / `rate_limited`.
- **Repair semantics.** The first invalid call (schema violation or unparsable JSON) to a tool gets a tool result "Invalid arguments ... call the tool again with corrected arguments" and counts as an offered repair; if a later step calls the same tool with valid arguments it is a repair (`repair: true`, counted), and if it is invalid again the call is a typed failure (`invalid_arguments_failed`, not run, counted), after which `onToolFailure` decides: `continue` (default; the model is told) or `stop`. Bookkeeping is **per call** (fixed after D39 first flagged it as a risk): each invalid call creates its own offer, an offer can be answered only in the **next** step (it expires after that), and an incoming call to the same tool answers the first unanswered offer in call order. So a valid call that arrives in the same step as an invalid one is never counted as a repair, two invalid calls get two offers, and a retry that is invalid again is exactly one failure. Remaining imprecision: the retry is matched to an offer by tool name and order, not by anything the model says, so a model that answers offer 2 before offer 1 is still matched in order.
- **Everything the model returns is untrusted:** tool names must be in the offered set (an unknown or hostile name gets an error result that quotes it JSON-escaped and capped at 64 characters, plus the list of real names); arguments are validated before anything runs and `execute` only sees validated data; results of tools are sent in `tool` messages wrapped in delimiters that carry a random per-result token and a sentence saying the content is data; they are **never merged into the system prompt** (the only addition to the system prompt is one fixed sentence, added when tools are offered, saying tool results are data; it contains nothing dynamic and can be switched off with `injectionNote: false`).
- **Results, errors, hangs:** results are cut at `maxToolResultBytes` (UTF-8 safe) with the marker `[truncated: N bytes omitted]`; a tool that throws or rejects becomes a typed `error` result (message redacted, 300 characters); a tool that does not finish within its timeout becomes a `timeout` result and its `AbortSignal` is aborted (JavaScript cannot stop code that ignores the signal, so such a tool may keep running in the background); parallel calls of one step run with a concurrency limit and their results keep the order of the calls.
- **Approval.** A tool marked `requiresApproval` is not run until the callback says yes, asked **after** the arguments validated and with the validated arguments, one call at a time. A denial gives the model "denied by user". **No callback means denied** (never run); a callback that throws means denied. Later phases will use this for anything that changes a database.
- **The run trace** (`RunTrace`) has steps, each model call (provider, latency, usage, finish reason, adapter quirks, routing from a fallback chain, typed error) and each tool call (arguments hash and size, latency, outcome, repair flag, truncation flag, approval state, result hash and size), and totals (model and tool calls, errors, repairs, failures, truncations, tokens with an `estimated` flag, wall time). Arguments and results are included only with `debug: true`, and then redacted. The whole trace passes through the redaction helper with the exact secrets the caller names; tests check that the key, a password in tool output and the delivered tool results do not appear in it.
- **What the prompt-injection tests show, plainly: they test the mechanics of the loop, not any model's resistance to injection.** The fake provider is scripted to behave as if it had obeyed an injected instruction; the tests check what the loop does then: a call to a tool that was not offered is an unknown-tool error and runs nothing; the injected text only ever appears inside a delimited tool message (never in the system prompt or a user turn) and not in the trace; and a call to an existing tool that needs approval still goes to the approval hook, whose answer is respected. Whether a real model would follow such text is untested here and no claim is made about it. The loop's defences are structural (offered set, validation, delimiting, approval), and a human approver is only as good as what they are shown.
- **Not done:** streaming inside the loop (it uses `chat`), tool results that are not text (images), per-call (rather than per-tool) repair tracking, persistence or resumption of a run.

## D40. Fallback chain, circuit breaker, quota tracking and the connection probe (C2.6)

- **When to fall over, and when not.** Fall over after `rate_limited`, `server_error`, `timeout`, `network`. Surface to the caller: `bad_request`, `auth_failed`, `content_filtered` (as you specified) and also `context_length`, `invalid_response` and `cancelled`, which were not on your list: another provider would not fix a context that is too long for the request, an unreadable response is more likely a bug than an outage, and a cancellation means the caller wants to stop. A provider that answered with a non-fallover error counts as **up** for its circuit. If you want `context_length` to fall over to a provider with a larger window, that is one line in `FALLOVER_KINDS`.
- **Circuit breaker** (injectable clock): closed; `failureThreshold` consecutive failures (default 3) open it; after `cooldownMs` (default 30 s) it is half-open and lets **exactly one** trial request through; success closes it, failure reopens it and restarts the cooldown. Tested with a manual clock: open, skipped with no request, half-open, recovery, and a failed trial.
- **Quota tracking:** per provider, sliding windows for requests and tokens per minute and per day as configured (tokens from the provider's usage, which may be estimated); a provider over its limit is **skipped without a request**. It is also updated from what the provider says: rate-limit response headers (`remaining` at 0 blocks until the reset) and `Retry-After` on a 429 block it until then, whatever the configured limits are. Not done: reading a provider's per-day limits from its API, and sharing counters between processes (the counters live in memory).
- **Routing is in the trace:** every result from the chain carries `routing { provider, skipped[] }` with the reason for each provider passed over (`rate_limited (HTTP 429)`, `circuit open (...)`, `quota exhausted (2/2 requests per minute)`, `does not support tool calls (probed)`), and the agent loop copies it into each step of the run trace. **Stickiness:** with a `conversationId` (the agent passes its run id) a conversation stays on the provider that served it last, while that provider is healthy; a new conversation starts at the top of the chain. A stream that has delivered content is never continued on another provider (that would splice two answers): it ends with a mid-stream error.
- **When everything is down:** one `LLMError` whose `causes` lists every provider with its reason, whose `kind` is that of the last real failure (or `rate_limited` when only quotas were hit, `server_error` when only circuits were open) and whose `retryAfterMs` is the earliest time any of them may be tried again.
- **The probe** (`testConnection`, `probeProvider`): model list (reachable, auth, model exists), a tiny chat call (latency), streaming, a **forced tool call** (`probe_echo`, first with the named `tool_choice`, then `required` if the server refuses the object form) whose returned arguments must be valid JSON and validate against the schema, and JSON mode. Each check is reported with evidence and a status (`pass`, `fail`, `inconclusive`, `skipped`). **A capability is `false` only on evidence** (a 400 refusal, no tool call, arguments that do not validate, a non-JSON reply in JSON mode); a timeout or a connection problem leaves it `null`/unknown, never `false`. Results are stored on the provider as capabilities labelled `probed` with the timestamp; `parallelToolCalls` and `maxContext` are not probed and stay unknown. A chain skips members probed as not supporting tools for requests that have tools, and `runAgent` refuses to start with tools on a provider (or chain) known not to support them (`capability_unsupported`, nothing is sent).
- **Limits of the probe:** a model that passes one forced tool call can still be unreliable at tool calling in general, and one that fails may have had a bad moment; the probe says what happened once. It is also not free (about five small requests), so it runs on demand, not before every call.

## D41. Bring-your-own-key safety: URLs, SSRF, key storage and redaction (C2.7)

- **What is built** (`core/src/security/`): `validateUrl` (HTTPS only; `http://` only for localhost/127.0.0.0/8/::1 and only when the **server-built policy** has `allowInsecureLocalhost`; no credentials, no fragment, no control characters, a maximum length of 2,048, no internal names such as `localhost`, `*.localhost`, `*.internal`, `*.local`, `*.lan`, single-label names, `metadata`; IP literals checked after the URL parser has normalised decimal, hex, octal and short forms; host allow and deny hooks); `classifyAddress` (IPv4: unspecified, RFC 1918, carrier-grade NAT, loopback, link-local including 169.254.169.254, IETF, documentation, benchmarking, multicast, reserved and broadcast; IPv6: only global unicast 2000::/3 is allowed, minus unspecified, loopback, **all IPv4-mapped and IPv4-compatible**, NAT64, Teredo, 6to4, documentation, ORCHID, unique local, link-local, site-local and multicast); `createSafeFetch`; `Keyring` with `encryptSecret`/`decryptSecret`; `redactText`/`redactDeep`/`redactingLogger`/`maskKey`.
- **The dev flag lives only in the policy object that server code passes to `createSafeFetch`.** Nothing reads it from a URL, a request or a stored provider config (a test passes a "user settings" object and a query parameter named like the flag and both change nothing). The flag allows http and loopback for localhost-type targets only: private ranges, metadata addresses, IPv4-mapped addresses and internal names stay refused with it on (tested).
- **Connection pinning.** The safe fetch validates the URL, resolves the host name **once** with the system resolver, requires **every** answer to be public (a mixed answer is refused), and connects to the validated IP address itself (`host` is the IP, `servername` and the `Host` header stay the original name, so the certificate is checked against the right name; an IP-literal URL gets no server name). A second DNS answer between the check and the connection therefore cannot matter: the rebinding test returns a public address first and a private one second, and shows the connection options carry the public address, the lookup function returns it, the resolver is called once per request, and the next request (now answered with the private address) is refused. Redirects are **not followed by default**; if `maxRedirects` allows them, every hop goes through the same validation and resolution, the count is capped, and `Authorization`, cookies and API-key headers are dropped when the origin changes. A connect timeout, a total timeout (which also bounds a stream's duration), a maximum response size (declared length, and bytes counted while streaming) and `Accept-Encoding: identity` apply; the adapter additionally limits stream events and idle time.
- **Key storage.** AES-256-GCM, a random 96-bit nonce per value, keys only in the environment (`LEDGERWORKS_SECRET_KEYS="id:base64,id2:base64"`, `LEDGERWORKS_SECRET_KEY_ID`), value format `lw1.<keyId>.<nonce>.<ciphertext>.<tag>`; the key id inside the value makes rotation possible (`needsRotation`, `reencryptSecret`, then the old key can be dropped, tested); an optional context (for example the config id) is authenticated, so a value copied to another row does not decrypt; every failure is the same generic `DecryptionError`. No database tables yet, as agreed.
- **Redaction** (`redactText`, `redactDeep`, `redactingLogger`, `maskKey` showing only the last four characters) is used by `LLMError` (so every error path), the agent trace, the smoke report and any logger built with `redactingLogger`. Tests check that the key (and URL credentials and a query string) do not appear in thrown errors, JSON of errors, the run trace (also with `debug`), the smoke output and a log line, including when the server echoes the Authorization header back in its error body and its text.
- **Remaining risks, honestly:**
  1. **DNS pinning and proxies.** The safe fetch connects directly and ignores `HTTP(S)_PROXY`. Behind a mandatory egress proxy the pinning is meaningless (the proxy resolves and connects), and the SSRF protection then has to live in the proxy or the network policy; if the application cannot connect directly, the safe fetch fails closed.
  2. **It depends on where it runs.** The checks use the resolver of the machine. In a network where internal names are public or resolve to public addresses (a public IP in front of an internal service, split-horizon DNS, an internal service reachable on a public address), nothing here can tell it is internal. It is not a substitute for egress filtering, and it needs the application to run somewhere that cannot reach the cloud metadata service through a public address.
  3. **Ports and destinations.** Any port on any public host is allowed: a user can make the server send requests to arbitrary public hosts and ports (port probing, a small relay for abuse), at the rate the application lets them. Per-user rate limits and a port policy are not built. A host allowlist hook exists and is the strong option for a hosted product.
  4. **IPv6 is an allowlist (2000::/3)**: addresses allocated outside it later are refused until the list is updated; the special-purpose lists are as of writing.
  5. **TLS** is Node's default verification against the host name; no certificate pinning, no minimum protocol setting here. An IP-literal HTTPS URL needs an IP SAN in the certificate.
  6. **Keys in memory.** A decrypted key is a JavaScript string: it cannot be wiped and can appear in a heap dump or a crash report. The key-encryption keys in the environment are as safe as the process environment. 96-bit random nonces are fine for this use (limits are around 2^32 values per key); rotation is manual.
  7. **Redaction is pattern-based** for anything that is not registered as an exact secret: a key in an unusual format that a third-party server echoes into an error message is caught only if the caller passes it in `secrets` (the adapter and the agent loop do for the configured key).
  8. **The dev flag** is dangerous if a production configuration sets it; it is a property of server code by design, but nothing prevents a deployment from turning it on.
  9. **Not tested:** real TLS handshakes and certificate checks, real DNS (the resolver is injected), IPv6 connectivity, behaviour behind a proxy or on Linux, and HTTP/2. The connection timeout is tested with a fake socket, not a black-holed address. Not built: a limit on the number of concurrent connections per user.

## D42. Text tool calls are opt-in and never for state-changing tools (fix of a D38 risk)

- **Change:** the adapter no longer reads a reply that merely looks like a tool call as one unless `acceptTextToolCalls: true` is set (default off). Even then it ignores the reply when any matched tool is marked `changesState` (a new optional field of `ToolDefinition`, copied from `AgentTool.changesState`, never sent to the server): that text stays text, and a reply that mixes a safe and a state-changing call is not read at all. Reason: D38 flagged that a model answering with exactly such JSON would be misread as a call; for a tool that writes that misreading would be an action nobody asked for.
- **Cost:** servers that really emit tool calls as text need the flag for each provider config; nothing else changes. The structured `tool_calls` path is unaffected.

## D43. Cancellation is part of the tool contract (fix of a D39 risk)

- **Problem (flagged in D39):** a tool that ignores its `AbortSignal` keeps running after a timeout; for a database tool that means a query keeps running on the server and holds a connection after the loop has moved on.
- **Decision:** the contract is written down (core/README.md): every tool gets a signal and must stop; the loop fires it, returns `timeout`/`cancelled` at once, waits a bounded grace period (`toolAbortGraceMs`, default 2 s) for the tool to actually settle, and marks a tool that did not as `abandoned` in the trace. Database tools use `withCancellableClient`, which cancels the query on the server (`pg_cancel_backend` from a second connection), drops the connection after `hardStopAfterMs` if needed, and releases it.
- **Alternative rejected:** `pg.Client` has no public cancel in the driver version in use, and destroying the socket alone relies on the server noticing a closed connection when it next checks (a running `pg_sleep` or a long scan notices late); `pg_cancel_backend` is explicit and observable in `pg_stat_activity`.
- **Verified against a real server:** `pg_sleep(30)` cancelled within about a second of the abort, no active query and no leftover connection after a tool timeout and after a run cancellation, and the contrast case reported as `abandoned`.
- **Remaining limits:** a tool that does non-database work and ignores the signal cannot be stopped; the second connection needs a free connection slot and the same role; with a connection pool, cancel only the connection that was checked out for the tool (the helper uses a dedicated connection per call).

## D44. Tool registry, the read-only Postgres tools and the MCP server (C2.8)

- **One definition per tool, one schema source.** The zod `input` schema validates arguments and produces the JSON Schema (`z.toJSONSchema`) given to models and to MCP clients, through one function (`inputJsonSchema`); a test compares what the agent loop and an MCP client receive, tool by tool (identical). The registry's type is called `ToolSpec` (not `ToolDefinition`, which is the LLM-layer type for what a model is shown). The registry refuses unsafe names, duplicates, contradictory annotations and state-changing tools without approval unless a reason is written in code.
- **MCP SDK: `@modelcontextprotocol/sdk` 1.32.0** (the official TypeScript SDK; a protocol library, not an LLM vendor SDK; MIT; peer dependency zod `^3.25 || ^4`, which matches ours). I use its low-level `Server`, `StreamableHTTPServerTransport`, `StdioServerTransport`, the client classes (in tests) and the in-memory transport, not its high-level `McpServer.registerTool`, because that converts zod schemas itself and would produce a second JSON Schema; the low-level server returns the registry's. I do not advertise `outputSchema` over MCP (clients validate it with their own JSON-Schema engine; the structured result is still returned and the `output` schema is enforced on our side). Risk: the SDK is young and fast-moving; the version is pinned by the lockfile.
- **Text from the database is untrusted data** (query text, identifiers, comments, definitions, plan node text): wrapped as `{ "$untrusted": ... }`, control characters, bidi overrides and zero-width characters removed, line breaks flattened, length limited. Identifiers are wrapped too: a table named like an instruction is as much an injection vector as a comment. The cost is noisier output. Tool results reach a model only as delimited tool messages (agent loop) or with a "this is data" header (MCP); nothing goes into a system message. As with D39, **the tests check the mechanics (marking, delimiting, where the text appears), not whether any model would follow such text.**
- **Literal redaction** (`redactLiterals`: strings, E-strings, dollar quotes, numbers, hex and bit strings become `?`) is on by default for `list_slow_queries` and set by server configuration. Found while testing: `pg_stat_statements` keeps utility statements with their constants, e.g. `ALTER ROLE ... PASSWORD '...'` is stored with the password in clear (the benchmark database's own role setup statements were in the list; the tool shows `PASSWORD ?`). Ordinary queries are normalised by PostgreSQL itself.
- **`get_query_plan` safety, in three layers:** (1) a text check that the input is exactly one SELECT or `WITH ... SELECT` after comments, strings, dollar quotes and quoted identifiers are blanked (so a semicolon or keyword hidden in them neither hides nor triggers a refusal; nested comments are read as PostgreSQL reads them), refusing write keywords, `INTO`, locking clauses, `EXPLAIN` and `ANALYZE` anywhere, and a list of dangerous functions; it errs towards refusing (a column called `set` or `lock` unquoted would be refused); (2) the statement runs as `EXPLAIN (FORMAT JSON)` without ANALYZE, so it is planned, not executed; (3) in a `READ ONLY` transaction with a statement timeout, as a role the readiness check has verified cannot write. There is no argument that could add ANALYZE (strict schema); a test shows `pg_stat_statements` call counts do not move. Parameterised queries get `GENERIC_PLAN` (PostgreSQL 16), labelled.
- **Plan text:** every string in the plan except PostgreSQL's fixed vocabulary (node type, join type, strategy, scan direction, ...) is wrapped as untrusted; `summary` carries our own booleans and the node-type list.
- **`describe_schema`:** partitions are listed under their parent and do not count against `max_tables` (up to 100 per parent, flagged when cut); indexes of a partitioned parent have no size of their own (`null`); row counts are `reltuples` estimates, labelled in a note; `shared_preload_libraries` is `null` when the role may not read it.
- **MCP over HTTP:** loopback default; token mandatory on every request (SHA-256 of both sides then `timingSafeEqual`), never logged (a test checks the log lines); `Origin` allow list defaulting to empty (any browser request is refused), `Host` must be `127.0.0.1`/`localhost`/`[::1]` with our port; 1 MiB limit (declared and streamed: answered with 413 and the connection closed); a fixed-window rate limit per client address that also counts unauthenticated requests (so guessing is slowed down); a cap of 20 sessions with idle expiry; one server per session; refusal to start on a non-loopback address without token and flag. **Remaining risks:** no TLS (loopback only; the token travels in clear on the local machine); the rate limit is per address, so every client behind one proxy shares it and it resets when the process restarts; the token is one shared secret (no per-user identity or revocation); tool calls open read-only connections to the source under the server's own role, so anyone with the token can read whatever that role can read (including query text in `pg_stat_statements`, and schema and plan information); sessions live in memory. **Public exposure is out of scope for now.**
- **Stdio** is the same server for the process that starts it; its stdout carries only protocol messages (tested). **The MCP Inspector was not run:** `pnpm mcp:inspect` only prints instructions and has been tested for its output; the Inspector itself was not started in this session.
- **Not done:** a tool that changes state (none exists yet; the registry and the MCP server are built so that adding one needs an explicit decision in two places), per-user authorisation, MCP resources and prompts, cancellation messages from MCP clients beyond what the SDK forwards as an `AbortSignal`.
- **A bug the tests found in my own tool:** `list_slow_queries` ordered by `calls` sorted as text ("6" before "53"): the select list casts `calls::text`, whose output name is also `calls`, and a bare name in `ORDER BY` resolves to the output column first. It is the same alias-shadowing trap as Ledgerline E1 (D-log), and is fixed by qualifying the column (`pss.calls`); the test that ranks by calls now guards it.
